# rt-browser

Lets the agent log into the local RealTime SIS test site and verify pages in a browser **without the
model ever seeing the credentials**.

## Pieces

| Piece | What it does |
|---|---|
| Browsers (`chrome.ts`) | One Chrome per target. Main checkout: port 9222, profile `~/.cache/pi-browser/chrome-profile`. Each rtw instance: its own port (claimed atomically from 9230-9329) and profile under `~/.cache/pi-browser/instances/<name>/`, so parallel worktree sessions never share tabs, focus, or cookies. Auto-started before any chrome-devtools MCP call or `rt_login`. The password manager is disabled in every profile. `/rtw rm` closes the instance's Chrome and deletes its profile. |
| Telling browsers apart (`chrome.ts`) | Each rtw instance's Chrome gets a toolbar color (Chrome's "autogenerated" theme, set in its profile's `Preferences` before launch) picked from 8 dark, saturated hues by its port, so instances running together get different colors; the main checkout stays default gray. The first window is titled `RT <instance>` / `RT main` (`--window-name`), which shows in Mission Control, the Window menu and Cmd-`. The pi status bar shows `RT: …` as a pill using the exact toolbar/tab-strip colors Chrome derives (measured values in `INSTANCE_THEMES`; re-measure via `chrome://theme/colors.css` if a Chrome update shifts them). A profile whose Chrome is already running picks up the color on its next launch. |
| chrome-devtools MCP | Registered by this extension (not `mcp.json`) at session start with `--browser-url` for the session's target, and re-registered if `rt_login` switches to another instance, so it always drives the same browser `rt_login` used. Don't add `chrome-devtools` to `mcp.json`: a file entry takes precedence. |
| `/rt-browser [district][@instance] [--force]` | You run it: opens the shared Chrome and logs into that target (default `realitdemo` on the detected instance), e.g. `/rt-browser realtime`, `/rt-browser realtime@g12996-dr`, `/rt-browser realtime@main`. Shows `RT: <district> @ <instance>` in the status bar, tells the agent which target is active, and approves browser use for that target for the rest of the session. |
| `rt_login` tool (`login.ts`) | Reads the credentials in-process, clicks through the self-signed cert warning (Advanced → Proceed), fills the login form, answers the security question, and returns only status + URL. Optional `district` (same `district[@instance]` syntax; defaults to the current target). If the browser is logged into a different district on that host (per the `DISTRICTID` cookie) it logs out first. |
| Worktree instances (`rtw.ts`) | At session start, runs `rtw url --json` in the cwd. In an `rtw` worktree (`~/code/realtime-wt/<name>`) the target host becomes `<name>.sis.localhost`; in the main checkout (or anywhere else) it stays `sis.localhost`. The active origin is added to the system prompt so the agent navigates to the right host. Before logging into an instance, `rtw url <name> --json` checks the container is running. |
| Permission prompt | Like git-guard: before the agent calls `rt_login` or any chrome-devtools MCP tool, you're asked **No / Allow once / Allow for this session**, with the target and its URL. Session approval for `rt_login` is per `district@instance`; switching asks again. Approvals reset on a new session. Without a UI (print/headless), agent browser use is blocked. |
| Guard | Blocks any tool call (bash, read, grep, codemode, ...) whose input references `realtime-test` / `login.env`, except read/write/edit of this extension's own files (symlinks resolved). |
| Redaction | Replaces credential values (raw, URL/form-encoded, JSON, and HTML-escaped) with `[REDACTED]` in chrome-devtools MCP and `rt_login` results. Some RealTime pages echo the password into hidden inputs (`prevalidateuser.cfm`, `validateUser2fa.cfm`). |

## Credentials file

`~/.config/realtime-test/login.env` (override with `RT_LOGIN_ENV`). Keep it `chmod 600`.

```
# {district} is replaced by the district name (default realitdemo). Without the placeholder,
# the first path segment is treated as the district.
RT_BASE_URL=https://sis.localhost/{district}/stay.cfm
RT_USER=...
RT_PASS=...
RT_SEC_ANSWER=...
# optional: "remember this computer" on the security-question page: 0=no, 1=today (default), 2=permanently
RT_REMEMBER_COMPUTER=1
```

`RT_SEC_ANSWER` is a single answer. The page asks a random question from the user's answered ones,
so give the test account the same answer for every question (or only one question).

## Worktree instances

`RT_BASE_URL` stays pointed at the main checkout (`sis.localhost`). An instance only prepends one
validated DNS label to that host (`<instance>.sis.localhost`), so credentials can never be sent to
any other host. Target syntax:

| Input | Target |
|---|---|
| `realitdemo` | that district on the current instance (detected from the cwd at session start) |
| `realitdemo@g12996-dr` | `https://g12996-dr.sis.localhost/realitdemo/...` |
| `realitdemo@main` | `https://sis.localhost/realitdemo/...` (main checkout) |
| `@g12996-dr` | default district on that instance |

Workflow: `rtw new <branch>`, `cd ~/code/realtime-wt/<name>`, start `pi`. Each host keeps its own
cookies, so main and worktree sessions don't interfere.

## Safety behavior

- **No retries on a wrong security answer.** Three wrong answers log the user out (`security/setRemember.cfm`), so the tool stops after one rejection.
- It also stops on 2FA, forced password change, or forced security-question setup. Fix those states on the test account by hand.

## Limits

- Screenshots (image content) can't be redacted. Password-type inputs are masked by the browser.
- The guard catches accidents; it isn't a sandbox. The agent's prompt guidelines tell it not to look for the file.

## Env overrides

`PI_BROWSER_CDP_PORT` (main browser, default 9222), `PI_BROWSER_PORT_MIN`/`PI_BROWSER_PORT_MAX` (instance range, default 9230-9329),
`PI_BROWSER_PROFILE_DIR`, `PI_BROWSER_CHROME_PATH`, `RT_LOGIN_ENV`, `RTW_BIN` (path to `rtw`; default: `rtw` on
PATH, else `~/code/containerization/containers/rtw`).
